# Работа с агентами на большом монорепозитории

Правила, выведенные из прогонов на `cms`: аудит из 28 агентов, исправления из 38, слияния и проверка.
Подходят любому проекту, где код разложен по независимым боксам и есть быстрые юнит-тесты и медленные браузерные.

## Роли

| Уровень | Кто | Что делает |
|---|---|---|
| Координатор | Opus (я) | делит работу, пишет брифы, проверяет, сливает итог, гоняет медленные тесты, отчитывается |
| Лид зоны | Claude Haiku 5.5, работник Orca | владеет одной зоной: делит её, запускает исполнителей, сливает их ветки, гоняет проверку пакета, отдаёт одну ветку |
| Исполнитель | opencode `deepseek-v4.1-flash`; простое — `hy4-flash-free` | одна узкая задача в своём worktree, точечные тесты, коммит, отчёт |

- **Не больше двух уровней.** Третий добавляет пересказ, но не скорость.
- **Всё запускается через Orca** (`orca orchestration worker-start …`), а не `nohup … &`. Тогда работники видны, Orca будит координатора по `worker_done`, можно задать вопрос (`ask`/`reply`) и направить (`send`). Работник, запущенный в фоне shell, может зависнуть незаметно.
- Лид — это работник Orca (`--agent claude --model haiku`), а не субагент инструмента Agent: того Orca разбудить не может.
- Модель выбирается по суждению, которое нужно: разбить, отбросить ложное, слить конфликт — это лиду; написать по ясному брифу — исполнителю.

## Ход большого прогона

1. **Аудит, только чтение, широко (20–50).** Один срез = домен × аспект: логика, UX, производительность, безопасность, контракт между пакетами, расхождение документации с кодом, качество тестов. Все читают один отдельный worktree и пишут отчёт в файл строгого формата. Конфликтов нет, тестов нет, нагрузка низкая.
2. **Разбор находок координатором.** Прочитать самые серьёзные и оценить качество. Разложить находки по зонам по пути файла: территории не пересекаются. Слабые отбросить, с миграциями отложить.
3. **Исправления, по зонам.** Лид на зону (или исполнитель на 10–15 находок). Каждый сначала проверяет находку по коду: аудит может ошибаться.
4. **Слияние в интеграционную ветку.** Сначала всё, что сливается чисто. Конфликтные ветки — по одной, с сохранением обоих исправлений.
5. **Миграции — отдельной волной** после слияния, от интеграционной ветки. Номера пересоздаются одной миграцией при сведении.
6. **Медленные наборы — координатор, последовательно:** полная проверка, браузерные, live. Падения раздаются агентам по набору, с портом на каждого.
7. **Итог в основную ветку**, отчёт пользователю, уборка веток и worktree.

## Бриф

Агент не видит моей памяти и разговора. В брифе всё, что ему нужно:

- что прочитать первым: правила репозитория, конвенции пакета, README каждого бокса, который он трогает;
- задача и её граница: какие папки его, какие чужие, чего не трогать (файлы, которые правит пользователь);
- запреты: без миграций (или одна), без браузерных тестов при параллельной работе, не пушить, не уходить с ветки;
- **никогда не удалять и не ослаблять проверки в тестах**, чтобы набор прошёл; если старый тест проверял неверное поведение, сказать об этом в отчёте;
- как доказать, что готово: какая команда должна пройти;
- формат отчёта: по пункту на находку `fixed | skipped (почему) | partial`, плюс файлы вне зоны.

Для аудита — жёсткий формат находки: id, серьёзность, вид, `файл:строка`, проблема со сценарием, предлагаемая правка, объём, нужна ли миграция, уверенность. Такой отчёт можно разобрать скриптом.

## Параллельность — её предел задаёт машина, а не схема

- **Без тестов** (аудит, правка без проверки): 20–50 одновременно, в теории до 100. Пределы — лимиты провайдера, память на каждый процесс, `bun install` на каждый worktree.
- **С тестами:** около 10–15 одновременных `check`. 38 сразу дали load ~178: тесты падали по таймаутам, 8 агентов умерли или зависли.
- Компромисс: исполнители правят и гоняют только тесты своих файлов; лид — проверку пакета после слияния; координатор — полный набор один раз.
- Браузерные и live-наборы — на фиксированных портах: никогда два одного набора разом. Разные наборы на разных портах можно параллельно.

## Слияние

- Конфликты растут с числом агентов на один код: из 38 веток 24 конфликтовали, обычно потому, что двое чинили одно место по-разному. Лучшее средство — заранее разделённые зоны, а не умное слияние потом.
- Сливающий читает намерение обеих сторон (сообщения коммитов), сохраняет оба исправления, а если исправили одно и то же по-разному — оставляет одно цельное и сохраняет проверки обоих тестов.
- После каждой ветки — проверка типов и тесты затронутого пакета; в конце — полная проверка. Нет ни одного маркера конфликта.

## Проверка работы агента координатором

Отчёт агента «всё прошло» — не доказательство. Проверять самому:

- `git log -2` у ветки: коммит на своей ветке, от правильной базы (агент иногда коммитит не туда);
- удалённые проверки в тестах: `git diff база..ветка -- '*test*' '*spec*' | grep -E '^-\s*(assert|expect)'`, каждую посмотреть — переписана или выброшена;
- нет ли тронутых чужих зон и запрещённых файлов;
- объём diff правдоподобен (нет массового переформатирования);
- полная проверка и медленные наборы — на интеграционной ветке, самому.

## Сбои и как их видеть

- Зависший агент: его лог не меняется, процесс жив. Через Orca это видно по `worker-show`; в фоне shell — только по времени изменения лога.
- Агент, закончивший работу, может не выйти. Отчёт есть — процесс можно остановить.
- Прерванного агента запускать заново **с продолжением**: «в worktree уже есть работа предшественника — проверь, доделай, потом остальное».
- Падение под нагрузкой проверяется прогоном теста отдельно, на интеграционной ветке и на основной: если падает и там — это не наше.

## Работа пользователя

- Незакоммиченные правки пользователя в основной ветке не трогать: агенты работают в worktree от последнего коммита, их файлы вписываются в запреты брифа.
- Готовое переносится в рабочее дерево основной ветки, там пользователь смотрит на своём dev-сервере; коммит — по его слову.
- Удаление веток, в том числе удалённых, — только после проверки, что всё в основной (`git rev-list --count main..ветка` = 0).
